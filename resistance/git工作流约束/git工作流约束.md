# git 工作流约束

本技能采用严格的功能分支策略，保证历史可追溯、可回滚、可合入。

## 规则

1. **启动前拉取**：开工前 `git fetch`；有远端更新先 `git pull --ff-only`，不得忽略。
2. **功能分支提交**：每个步骤完成后提交到 `feature/<topic>`，分支名不得为 `main`/`dev`。
3. **审核通过合 dev**：双链辩论通过且悬空链接为 0 后，把功能分支合入 `dev`。
4. **整体审查通过合 main**：审查标准全部通过后 `dev` 合入 `main`。
5. **禁止直写 main/dev**：所有变更必须经功能分支进入，`main`/`dev` 不接受直接 commit。
6. **重试熔断**：任一审查步骤失败且重试达 10 次，触发惩罚机制，回退分支或求助用户。
7. **忽略清单**：`.gitignore` 必须含 `tmp/` 与 IDE 目录；暂存前核对 `git status`。
8. **自动 init**：操作仓库前检查 `.git/`，未初始化即 `git init`，不得跳过。
9. **推送前确认**：推送远端前**必须**取得用户确认；未确认不得 `git push`。
10. **仓库可见性**：可能含侵权/危害内容或用户须保密部分的仓库必须 PRIVATE；
    其余 PUBLIC；判定不了就问用户，不得擅自设 PUBLIC。
11. **附属技能双仓**：附属/私有子技能同样必须入库，进的是独立 PRIVATE 伴生仓
    （本体仓 PUBLIC 且 ignore `private/`）；不入库或误推公开仓均视为泄漏。

## 违规后果

- 跳过功能分支：main/dev 被污染，无法按步回滚；
- 未确认即推送：未经同意发布到远端，不可撤回；
- 漏配 ignore：过程工件入库，污染历史；
- 附属内容进公开仓：私有内容外泄（`E_LEAK_TO_PUBLIC`），不可撤回。
